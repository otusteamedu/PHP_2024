# Кейсы тестирования бэкенда страницы оплаты

---

## 1. Модульные тесты (Unit Tests)
Модульные тесты проверяют только логику бэкенда (контроллера), изолируя его от внешних зависимостей (репозитория и сервиса A). Предполагаем, что валидация данных происходит в контроллере, и тестируем все возможные случаи невалидных данных.

1. **Если `card_number` содержит менее 16 цифр**, то метод возвращает HTTP-код 400 с сообщением "Неверный номер карты".
2. **Если `card_number` содержит более 16 цифр**, то метод возвращает HTTP-код 400 с сообщением "Неверный номер карты".
3. **Если `card_number` содержит не только цифры**, то метод возвращает HTTP-код 400 с сообщением "Неверный номер карты".
4. **Если `card_holder` пустой**, то метод возвращает HTTP-код 400 с сообщением "Укажите владельца карты".
5. **Если `card_holder` содержит более одного пробела подряд**, то метод возвращает HTTP-код 400 с сообщением "Неверный формат имени владельца".
6. **Если `card_holder` содержит символы, кроме латинских букв, пробела и дефиса**, то метод возвращает HTTP-код 400 с сообщением "Неверный формат имени владельца".
7. **Если `card_expiration` не в формате мм/гг (например, "21/30")**, то метод возвращает HTTP-код 400 с сообщением "Неверный формат даты окончания".
8. **Если `card_expiration` указывает прошедшую дату (например, "01/25" при текущей дате "02/25")**, то метод возвращает HTTP-код 400 с сообщением "Срок действия карты истек".
9. **Если `cvv` содержит менее 3 цифр**, то метод возвращает HTTP-код 400 с сообщением "Неверный CVV-код".
10. **Если `cvv` содержит более 3 цифр**, то метод возвращает HTTP-код 400 с сообщением "Неверный CVV-код".
11. **Если `cvv` содержит не только цифры**, то метод возвращает HTTP-код 400 с сообщением "Неверный CVV-код".
12. **Если `order_number` пустой**, то метод возвращает HTTP-код 400 с сообщением "Укажите номер заказа".
13. **Если `order_number` длиннее 16 символов**, то метод возвращает HTTP-код 400 с сообщением "Неверный номер заказа".
14. **Если `sum` пустая или не содержит числового значения**, то метод возвращает HTTP-код 400 с сообщением "Укажите сумму оплаты".
15. **Если `sum` содержит отрицательное значение**, то метод возвращает HTTP-код 400 с сообщением "Сумма не может быть отрицательной".
16. **Если все данные валидны**, то метод передаёт запрос в сервис A (проверяем вызов сервиса через mock-объект).

## 2. Интеграционные тесты (Integration Tests)
Интеграционные тесты проверяют взаимодействие между модулями: «фронт-бэк», «бэк-сервис A» и «бэк-репозиторий». Поведение фронта при ошибках будет консистентным: при ошибке 400 поле с неверными данными выделяется красной рамкой, при ошибке 403 — отображается сообщение "Не удалось списать средства, проверьте данные".

### a. Связка «фронт-бэк»
1. **Если `card_holder` содержит более одного пробела подряд**, то после ответа бэка с кодом 400 фронт выделяет поле "Владелец карты" красной рамкой.
2. **Если `cvv` содержит 2 цифры вместо 3**, то после ответа бэка с кодом 400 фронт выделяет поле "CVV" красной рамкой.
3. **Если данные валидны, и сервис A вернул 200**, то фронт перенаправляет пользователя на страницу просмотра фильма.

### b. Связка «бэк-сервис A»
1. **Если данные валидны, но сервис A возвращает 403 (недостаточно средств)**, то бэк возвращает фронту код 403 с сообщением "Не удалось списать средства".
2. **Если данные валидны, и сервис A возвращает 200**, то бэк вызывает метод репозитория для записи успешной оплаты.
3. **Если сервис A недоступен (например, timeout)**, то бэк возвращает фронту код 500 с сообщением "Ошибка сервера, попробуйте позже".

### c. Связка «бэк-репозиторий»
1. **Если сервис A вернул 200, и метод `setOrderIsPaid` вернул true**, то бэк возвращает фронту код 200 с сообщением "Оплата успешно завершена".
2. **Если сервис A вернул 200, но метод `setOrderIsPaid` выбросил исключение (несоответствие суммы)**, то бэк возвращает фронту код 500 с сообщением "Ошибка записи оплаты".

## 3. Системные тесты (System Tests)
Системные тесты проверяют работу всей системы end-to-end, включая поведение пользователя и фронта.

1. **Если `cvv` неверен (например, "12a")**, то после отправки формы и ответа бэка с кодом 400 на фронте поле "CVV" выделяется красной рамкой.
2. **Если данные валидны, но на карте недостаточно средств (сервис A вернул 403)**, то на фронте отображается сообщение "Не удалось списать средства, проверьте данные".
3. **Если все данные верны, и оплата прошла успешно**, то пользователь перенаправляется на страницу просмотра фильма, а в БД фиксируется оплата.
4. **Если пользователь ввел истекшую дату окончания действия карты (например, "12/24")**, то после ответа бэка с кодом 400 на фронте поле "Дата окончания" выделяется красной рамкой.

## 4. Оптимизация затрат
1. **Использование моков и заглушек**: Для тестирования взаимодействия с внешними сервисами можно использовать моки и заглушки, чтобы избежать реальных транзакций.
2. **Тестирование в песочнице**: Большинство платежных систем предоставляют песочницу для тестирования, где можно проводить транзакции без реальных средств.
3. **Использование CI/CD**: позволит автоматически запускать тесты при каждом внесении изменений в код приложения.
